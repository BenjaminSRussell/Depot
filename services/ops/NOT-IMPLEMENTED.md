# NOT-IMPLEMENTED: ops (PSG-50, parts 1 to 3)

Built in part 2: failover step executors behind interfaces with a dry run, the `passage-ops` CLI, the fenced-region 503 in
`platform/go/httpx`, break-glass for `ops.failover.execute`, the lag reporter, `/healthz/region` through its own gateway listener, the
failover scorecard, tenant licences (signed install and state), the `passage_ops_*` and `passage_license_days_to_expiry` metrics, and the restore drill
and masked clone in `tools/tenant-restore`. Built in part 4: provisioning and decommission runners behind interfaces, `passage-ops tenant`, audited decommission routes, the monthly metering job and PDF statements, the licence user-count reporter, per-operation SLOs, masked-clone schedules and their job, the `outbox-ops` connector. Built in part 3: `GET /v1/ops/slo`, tenant provisioning (residency check, plan and step
tracking), tenant cost statements, licence user counts with the hourly licence check, the ops outbox and its four events, and the web operations
console. See the README.

| Item | Reason |
|---|---|
| Running the executors against real clusters (CNPG, Strimzi, Temporal, the DNS provider) | needs two live regions (#213). The adapters are tested against a fake Kubernetes API, a fake command runner and a fake webhook only; the CNPG patch shape (`spec.replica: null`, `cnpg.io/fencedInstances`) follows `deploy/multi-region/chart` but has not met a real operator |
| A DNS provider adapter | the provider is not chosen (cloud-agnostic ADR); the executor posts to a provider-neutral webhook (`OPS_DNS_WEBHOOK_URL`) that the provider's Terraform or a small function must serve |
| A ledger hash-chain verification endpoint | the ledger has no verification route. The step runs a configured command (`OPS_CHAIN_VERIFY_CMD`, for example `baseline.py verify`); until the ledger owner ships a per-tenant chain check the real verifier is the game-day tooling |
| Scaling application pods down and back up during a failover | the fence is the CNPG fence plus the 503 in every service; the runbook's pod scale steps stay manual (they need the Argo CD apps of both regions) |
| Rolling `global.regionFenceUrl` into every environment's values | the helper in `passage.cloudEnv` is in every service chart; each environment sets `global.regionFenceUrl` to its ops `/healthz/region`. Not set here: it needs the ops Service URL per environment |
| Break-glass reaching identity's elevated sessions | the window is checked in this service and logged in `ops_break_glass_use`; it is not a role assignment, so identity's effective-permissions view does not show it |
| Game-day scheduling (Temporal workflow with human tasks), fail-back dry run | needs two live regions; the scorecard measures a recorded failover |
| The fence for Kafka consumers and background workers | the 503 covers the HTTP API of services on `httpx`; finreport's share-link download is wrapped in `httpx.FenceMiddleware`; consumers and background workers are stopped by the database fence and by scaling them to zero (runbook "What the fence does not cover") |
| Fence at start-up when the role cannot be read | a pod that starts while `/healthz/region` is unreachable or answers no role serves as not fenced (fail open) and keeps the last state afterwards; failing closed would take a healthy region down whenever ops restarts |
| Licence rollback beyond `issuedAt` | an older licence cannot replace a newer one (issuedAt is the sequence); a licence reissued the same day, or a signed licence with a later issuedAt but worse terms, is accepted: the signer's discipline is the control |
| Real provisioning adapters (Keycloak realm, databases and RLS schemas, Kafka ACLs and topics, lakehouse namespace) | the runner, its four interfaces (`internal/provision`), the dry run, the `passage-ops tenant provision` command and the guarded, audited, reverse-order, idempotent `passage-ops tenant decommission` are built and tested with fakes. Only the `LogAdapter` exists: it logs what would change and says so in the step detail, because no Keycloak admin client, database owner role, Kafka admin API or lakehouse client the ops service can use is in the repository (identity holds the Keycloak admin client in its own module). A real adapter implements the same four interfaces and is passed in through `deps.provisioners`. Decommission has no data export step or second approver yet: the guard is "identity reports the tenant suspended", plus the audit trail |
| Live proof of the metering job | the job (`MeterOnce`, hourly check tick, idempotent per tenant and month) and the PDF statements (`GET .../costs/{month}?format=pdf` through print) are built. It reads the quantities with the PromQL set in `OPS_METER_QUERIES`; the container, CNPG, topic, object-store and model-token series must carry a tenant label in a live cluster. The EUR rate is one configured value (`OPS_USD_PER_EUR`), not an ECB month-average lookup |
| Licence classes on a user | the reporter is built (`ReportUsersOnce` counts active named users per licensed tenant from identity's `GET /v1/tenants/{id}/user-counts` as service:ops-reporter, every hourly tick). Identity has no licence class on a user yet, so every active user is reported as a full user and the operational and self-service counts are 0 |
| Per-operation SLOs in the hourly check and the console | per-operation objectives (`SLO_OPERATIONS`, route label of `http_requests_total`) are evaluated in `GET /v1/ops/slo` under `operations`. The hourly check and `slo.breached` stay per service; the FR-50.1 rows themselves are configuration (chart `slo.operations`), not shipped values; the ops console does not show the operation lines yet |
| Live relay of the ops outbox | the `outbox-ops` connector, its ACL literals, `debezium-cdc-ops` secret and role entry, and the ops migrations `0007_cdc_publication` and `0008_cdc_role_grants` are in the repository (routing is checked by `deploy/scripts/test_argocd_apps.py`). In each environment the `passage_ops` database and the `debezium_cdc_ops` role (REPLICATION) must exist and the Vault key `passage/<env>/ops-postgres/cdc-password` be written |
| Masked-clone job in the cluster | schedules (`/v1/ops/clone-schedules`), the claim-once-per-period runner and the `tenant-restore clone --apply` command runner are built (`OPS_CLONE_ENABLED=true`). `tenant-restore` must be in the image or a sidecar with `PASSAGE_CLONE_SOURCE_URL` and `PASSAGE_CLONE_TARGET_URL` in its environment, and the mask files must be mounted; none of that is in the chart image yet |
| Live proof of any of the above | needs two regions (#213) |
