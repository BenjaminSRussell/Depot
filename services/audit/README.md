# audit

Append-only field-level audit log for Depot (wave 5). Changes arrive two ways: from a verified service through `POST /v1/audit/changes`, and from the audited tables of the owning services through the CDC consumer (`audit cdc-consume`, B-07, below). Each row is hash-chained; updates and deletes are rejected by a trigger. The chain is verified nightly and its head anchored once a day.

Run: `DATABASE_URL=postgres://... MIGRATE_ON_START=true go run ./cmd/audit`. Test: `go vet ./... && go test ./...`; store tests need `DEPOT_TEST_DATABASE_URL`. RLS proof also needs `DEPOT_TEST_APP_DATABASE_URL` as `depot_app`.

## Configuration

| Variable | Meaning |
|---|---|
| `DATABASE_URL` | required; Postgres URL, from a Secret in the cluster |
| `MIGRATE_ON_START` | `true` applies embedded migrations at start (dev only) |
| `HTTP_ADDR`, `ADMIN_ADDR` | default `:8080`, and `:9090` serving `/metrics` only |
| `KAFKA_BROKERS`, `KAFKA_GROUP`, `KAFKA_USERNAME`, `KAFKA_PASSWORD_FILE`, `KAFKA_TLS_CA_FILE` | `audit cdc-consume` only (platform `eventing/kafka`); group `audit-cdc` |

Commands: no argument serves the API. `audit cdc-consume` runs the CDC consumer (chart `consumer.enabled`, Deployment `<release>-cdc`, one replica, admin port `/healthz`, `/readyz`, `/metrics`). `audit chain-nightly <tenant-id>...` verifies and anchors (chart `chainNightly`, a CronJob at 01:43 UTC). Both start only while their service principal (`audit-cdc`, `audit-anchor`) is seeded in `platform/go/tenant`.

## Who made a change (B-06, AUD-API-1, FR-5.10)

What is guaranteed for every change recorded from this release on:

- **Only a verified service records a change.** `POST /v1/audit/changes` needs a service token (`X-Depot-Service-Token`, ADR-0010) that the audit service verified itself. A call with identity headers only (`X-Depot-User`, `X-Depot-Duties`) is refused with 403 AUD-0007: audit has no gateway route, no NetworkPolicy and no gateway secret in Kubernetes, so those headers prove nothing here. No person calls this route today; changes made by people directly reach the trail through CDC (B-07, below), which records `actorKind` `person`.
- **The actor is the verified caller, never a body value.** A body that sets `userId` (any value, the caller's own included) is refused with AUD-0002, as for the read log. The service derives the actor from the verified token:

| Token | `userId` | `actorKind` | `onBehalfOf` |
|---|---|---|---|
| `act` is a service principal (`service:<name>`, accepted only from that principal's own issuer) | `service:<name>` | `service` | empty |
| `act` is an end user | `service:<calling service>` | `service` (`agent` when the issuer is `agents`) | the end user |

- **The body can only restate the actor.** `actorKind` and `onBehalfOf` are optional. `onBehalfOf` from a service acting on its own, or naming anyone but the user the token carries, is refused with AUD-0006, and so is an `actorKind` that differs from the derived one. `onBehalfOf` is the user the calling service put in its signed token: the audit service verifies which service vouches for that user, not the user's own sign-in. The History panel can therefore show "Recorded by Billing service for Ana Ruiz".
- **The database enforces the same shape** for rows with an `actorKind`: a service or agent is a `service:` id and a person never is, and only a service or agent has an `onBehalfOf`.

A change also carries `reason` (up to 1,000 characters), `changeSetId` (the field changes of one save), `eventType` and `eventId` (the business event that carried it) and `workflowInstanceId` (each up to 256 characters). Limits count characters, as OpenAPI `maxLength` and Postgres `length()` do; text must be valid UTF-8 without NUL. These are columns of `audit_entry` (migrations `0005_change_actor_context.sql`, columns and `NOT VALID` checks under a 5 s lock timeout, and `0006_change_actor_context_validate.sql`, which validates them without the exclusive lock). They are returned by `GET /v1/audit/records/{entity}/{recordId}` and published on `dev.depot.audit.change.recorded.v1`, absent when empty in both. Appends are serialised per tenant with an advisory lock, as for the read log, so concurrent changes cannot fork the chain. `occurredAt` is stored in UTC truncated to microseconds (the precision of `timestamptz`), and the hash is computed over that value, so every row's hash recomputes from the database.

**Hash encoding, for outside verifiers.** `hash` is the lowercase hex SHA-256 of one of three payloads, chosen per row:

- *v3* (B-07), when any of `legalEntityId`, `source`, `flag` is non-empty (every captured change, and every change a service records with a token naming one legal entity): the v2 array below with its first element `"audit-change-v3"` and `legalEntityId` (lowercase hyphenated UUID), `source` and `flag` appended, in that order, serialized the same way. `TestV3HashKnownAnswer` pins two vectors.

- *v2*, when any of `actorKind`, `onBehalfOf`, `reason`, `changeSetId`, `eventType`, `eventId`, `workflowInstanceId` is non-empty and no v3 field is (a row this API writes for a token that names no single legal entity, and every row written between B-06 and B-07): the RFC 8785 (JCS) serialization of the JSON array of strings `["audit-change-v2", prevHash, entity, recordId, field, oldValue, newValue, userId, actorKind, onBehalfOf, traceId, occurredAt, reason, changeSetId, eventType, eventId, workflowInstanceId]`. In practice: no whitespace; in strings only `"` and `\` are escaped, plus `\b \t \n \f \r` and `\u00xx` (lowercase hex) for the other control characters; everything else (`<`, `>`, `&`, U+2028, U+2029, non-ASCII) is written as UTF-8. `occurredAt` is UTC, truncated to microseconds, in RFC 3339 with trailing fractional zeros dropped (`2026-11-01T09:00:00Z`, `2026-11-01T09:00:00.1234Z`). `json.dumps(values, ensure_ascii=False, separators=(",", ":"))` in Python produces the same bytes; `TestV2HashKnownAnswer` pins a vector.
- *legacy*, for rows written before AUD-API-1 (all of those fields empty): `prevHash|entity|recordId|field|oldValue|newValue|userId|traceId|occurredAt`, joined by `|`, with `occurredAt` in UTC as RFC 3339 with up to nanoseconds. Legacy rows keep the hash they were written with, and this release rewrites none of them. That does not mean every legacy row re-verifies from the database: before B-06 a row was hashed over the `occurredAt` it was given, up to nanoseconds, while `timestamptz` keeps microseconds. A legacy row whose time had a sub-microsecond part cannot be re-verified from the stored values. That covers every row that took the handler's default of `time.Now()`, and every engineering signature. Its stored hash is still the one computed when it was written; the information needed to recompute it is gone. A verifier must report such a row as a known legacy-precision break, not as tampering (AUD-API-4). A legacy row whose time had no sub-microsecond part re-verifies. The legacy payload is ambiguous where a field holds a `|`: a `|` moved between neighbouring fields leaves the payload, and the hash, unchanged, so a verifier reports such a row as a known legacy-ambiguous break (it recomputes, but its field boundaries are not proven).

A v2 change must be valid UTF-8 (RFC 8785 is defined only for that). `domain.Hash` returns no hash for one that is not, `domain.Verify` reports it as a break, and validation refuses it, so two values that differ only in invalid bytes can never collide.

**Rollout (deliberately not N/N-1 compatible with engineering).** A new audit service refuses an old engineering's `userId` (AUD-0002), and an old audit service refuses a new engineering's `onBehalfOf` and `reason` as unknown fields. Deploy audit first, then engineering. Signature records queue in engineering's `audit_outbox` meanwhile and its relay retries with backoff (at most 15 minutes between attempts), so they arrive once engineering is upgraded. Rolling audit back stalls signature delivery until audit is rolled forward again; nothing is lost.

While old audit replicas still run during the rollout, they take no advisory lock, so they can fork a chain together with the new replicas. They also still accept identity headers and a body `userId`. Roll audit out for this release without old and new replicas serving together. Set the chart's `strategy` (new value, empty by default) for this release only, for example `--set strategy.type=Recreate`, or in the environment values `strategy: { type: Recreate }`. Then remove it again. `maxSurge: 0` alone is not enough: with the default `maxUnavailable` some old replicas keep serving next to new ones. Use `maxSurge: 0` with `maxUnavailable: "100%"`, or Recreate. Audit is unavailable for the few seconds the new pods take to become ready; engineering's relay retries.

## Changes captured by CDC, with depot.ctx (B-07a, architecture gap D3, FR-5.10, FR-5.11)

**Where changes come from.** A service that owns an audited master-data table does not call audit. Its database is captured: an `audit-cdc-<service>` connector (`deploy/kafka/connect.yaml`, a connector type separate from the `outbox-<service>` relays) streams the row changes of the service's publication `depot_audit_<service>` and the service's `depot.ctx` messages to one topic, `depot.cdc.<service>`, declared as a KafkaTopic with one partition and 30 days of retention. `audit cdc-consume` reads it with the platform `eventing` consumer (its `Config.Decode` hook turns Debezium records into events) and the platform inbox, so it is idempotent by CDC position (`<source>:<txId>:<lsn>:<table>:<id>`). Each insert, update or delete becomes one chain row per changed field of the table's allow-list (`internal/cdc/tables.go`): an insert records each non-empty field from `""`, a delete each non-empty field to `""`, an update each field whose value differs. `occurredAt` is the source commit time, `entity` the table (`vendor_bank_account`), `recordId` its key, `legalEntityId` the row's legal entity, `source` the owning service. Snapshot reads, truncates and the connector's heartbeat records are skipped; a change of a table the registry does not know is dead-lettered to `consumer.kafka.dlqTopic` (default `depot.audit.cdc.dlq`). The pilot table set is party's vendor bank accounts (party migration `0021`; party's add-bank-account path writes `depot.ctx`).

**P3 columns.** They are never in the allow-list and never written to Kafka, but they do leave the source database as ciphertext: `account_number_sealed` and `routing_number_sealed` (AES-GCM, `fieldcrypt`) are in the WAL, in the old row too under REPLICA IDENTITY FULL, and pgoutput streams them over the replication connection to Kafka Connect, where `column.exclude.list` drops them. A publication column list cannot leave them out while the replica identity is FULL. The CDC role holds a column-level SELECT without the sealed columns (party `0021`, and `0022` for a database that applied the first 0021); with `snapshot.mode: no_data` it never selects rows anyway.

**depot.ctx: who, why and which trace (design).** The architecture's design (§7.16, E.1 step 3): the writing service emits a transactional logical-decoding message with the prefix `depot.ctx` at the start of the transaction that changes an audited table (`platform/go/auditctx`: `WithAuditedTx`, or `Emit` before the first audited change; `pg_logical_emit_message(true, 'depot.ctx', …)`). Debezium (pgoutput, `message.prefix.include.list: depot.ctx`) decodes it with the transaction's changes, in commit order, and the single partition keeps it ahead of them. The body carries `{v, tenantId, actor, actorKind, onBehalfOf, reason, traceId, changeSetId, eventType, eventId, workflowInstanceId}`. We chose it over a per-service `audit_ctx` row or a trigger-captured setting because it needs no table, trigger or grant in the owning service, adds nothing to the service's own data, and cannot be read back or updated by the service afterwards; its cost is one WAL record per audited transaction (it also assigns the transaction an id, so it is not emitted in read-only transactions). The actor comes from the verified principal of the request, never from input: a person signed in through the gateway is `person`; a service token whose act is a service principal, or an in-process consumer, is `service:<name>` (`service`); a service token carrying an end user is `service:<issuer>` (`service`, or `agent` for the agent runtime) with `onBehalfOf` the user. The reason is the `X-Depot-Reason` header (up to 1,000 characters), which `httpx.NewRouter` captures (`auditctx.Capture`) for every service; the trace id is the W3C trace id of a `traceparent` header, else the request id; `changeSetId` is new per transaction (one save). **The reason and the trace id are client input and not authenticated:** a client can send another request's trace id. They say what the client claimed; neither is an authority field.

**The message is signed (ADR-0010 key).** Any session on the source database (`depot_app`, the owner, the CDC role, an ops tool, an injected query) can call `pg_logical_emit_message`, so the body alone proves nothing. `Emit` wraps it in an envelope `{v: 2, body, txid, iss, kid, sig}`: `txid` is `txid_current()` read in the same transaction, and `sig` is the emitting service's Ed25519 signature with its existing service-token key (`DEPOT_SERVICE_SIGNING_KEY[_FILE]`, `DEPOT_SERVICE_KEY_ID`; party calls `auditctx.ConfigureSigner` at start) over the domain `depot.audit-ctx.v1.`, the tenant, the txid and the exact body bytes (`tenant.ServiceSigner.SignDetached`, which refuses the service-token domain, so a signature never doubles as a token). The consumer verifies it against the source service's public key from the same registry the API verifies service tokens with (`DEPOT_SERVICE_NAME=audit`, `DEPOT_SERVICE_PUBLIC_KEYS`, chart `serviceIdentity.publicKeys`), requires the issuer to be the service whose database the change came from, and requires the signed txid's low 32 bits to equal the message's Debezium `source.txId` (the BEGIN xid; `txid_current()` adds the epoch above it). An unsigned message, an unknown key or kid, another service's key, an altered body or txid, or a valid message replayed into another transaction is stored with `verified = false` and the reason, logged, counted (`audit_cdc_contexts_rejected_total`), and its changes are recorded as `system`, flag `unattributed-bad-signature`: the actor it names is never recorded. A service without a signing key still writes the message unsigned (and logs it once), so its changes are flagged rather than refused. A database credential alone can therefore not attribute a change to anyone; forging an attribution needs the service's signing key.

**What is guaranteed for a captured change:**

- It carries the actor, reason and trace id of the verified `depot.ctx` message its own transaction wrote, or it is flagged. No message, or only one of another tenant, gives `unattributed`; a message that does not verify gives `unattributed-bad-signature`; a verified message whose actor does not have its kind's shape (a "person" that is a `service:` id, an emitting service's defect) gives `unattributed`. Flagged changes are recorded with `actorKind` `system`, `userId` `system:<source>`, `traceId` and `changeSetId` `cdc:<source>:<txId>`. The database refuses `system` without a flag and a flag without `system` (migrations `0009` and `0011`).
- A message attaches only to changes after it in its own transaction (same source, `txId`, an earlier position) whose commit time is within an hour of its own (`cdc.ContextWindow`): both carry the transaction's commit time, and an older transaction that reused the 32-bit xid is days away. A 24-hour window would not do: 2^32 xids pass in about a day at 50,000 writing transactions a second.
- It is on the tenant's one hash chain, under the same per-tenant advisory lock as HTTP ingest, with alerts and `change.recorded` as before, and `legalEntityId`, `source` and `flag` are covered by the hash (v3 above).
- The pipeline is at-least-once and idempotent: a redelivered record is skipped by the inbox; a consumer restart between a message and its changes still finds the message in `cdc_tx_context`. Messages are kept seven days; the consumer purges older ones itself (at most hourly per tenant), and so does the nightly job.
- **Replaying from the dead-letter topic** has two limits. A row change replayed more than seven days after its message was received finds no message and is recorded as unattributed. A `depot.ctx` message that was dead-lettered and is replayed after its changes were appended does not change them: the chain is append-only. Replay messages before changes, and within the retention.

**Legal entity (D17 for audit).** `audit_entry` and `alert_inbox` carry `legal_entity_id` with the restrictive `<table>_legal_entity_scope` policy. It admits NULL, allowlisted in `platform/go/rlsexempt`: a NULL legal entity is a tenant-level entry (a tenant-level record, a token naming no single legal entity, every row from before B-07, including legacy rows that belong to a legal entity) that every reader of the tenant sees. `GET /v1/audit/records/...` and `GET /v1/audit/alerts` are filtered by the caller's scope. A change recorded over HTTP is filed under the one legal entity the service token names. The chain itself is one per tenant: the store appends, verifies and anchors in a transaction with `depot.legal_entity_scopes` `*` (`chainTx`, store-internal), an append returns nothing about other rows, and the verification verdict is given only to a caller with tenant-wide authority (below). `phi_read`, `phi_read_review`, `alert_rule`, `cdc_tx_context`, `audit_anchor` and `consumer_inbox` are tenant-level by design and have no legal-entity column.

**Verification (AUD-API-4) and the daily anchor (FR-5.11).** `GET /v1/audit/records:verify` walks the tenant's chain from the genesis hash (or the seq range `fromSeq`..`toSeq`, trusting the range's first `prevHash`). Because any verdict describes every legal entity's activity, it needs tenant-wide authority besides `audit.verify`: no legal-entity claim and the all-scope duty (with the ALL-scope header), or a tenant administrator (`dbx.TenantWide`); anyone else gets 403 AUD-0009. One request walks at most 100,000 rows (`store.MaxVerifyRows`): a longer walk answers `complete: false` and `nextFromSeq`; ask again from there and check that the page's `startPrevHash` is the previous page's `head`. A page that stops also checks that the next page's first row links to its last row, and keeps any anchor whose head lies between the two, so a row removed exactly at a page boundary fails the page that ends there. The verdict has `verified`, `entries`, `fromSeq`, `toSeq`, `startPrevHash`, `head`, `breaks` and `firstBreak` (`seq`, `id`, `kind`: `hash-mismatch` a value changed, `link-mismatch` a row removed, inserted or reordered, `fork` a row that recomputes but links to one of the last 10,000 rows other than the one before it, `anchor-mismatch` an anchored head the chain no longer holds), `knownBreaks` and `anchors`. After a break it goes on from the broken row's stored hash, so one changed row is one break. Known legacy breaks do not fail verification and are counted apart: `legacyPrecision`, a row from before B-06 hashed over a sub-microsecond `occurredAt`, whose hash is recovered by trying the 999 nanoseconds the stored microsecond can hide (a legacy row no offset recovers is a `hash-mismatch`); `legacyFork`, two legacy rows linked to the same predecessor by the unserialised appends before B-06; `legacyAmbiguous`, a legacy row with a `|` in a field, which recomputes but whose field boundaries the `|`-joined legacy payload cannot prove (a `|` moved between neighbouring fields keeps the hash). `audit chain-nightly <tenant-id>...` (CronJob) verifies each tenant's whole chain, writes the day's anchor in `audit_anchor` (head seq and hash, entries, verdict; one row per tenant per UTC day, append-only; a rerun keeps the first), logs it as one JSON line (`audit chain anchored`, the copy outside the database) and purges week-old `depot.ctx` messages. `depot_app` cannot insert anchors: they go through the SECURITY DEFINER function `audit_anchor_record` (migration `0014`, replacing `0011`'s and `0013`'s). It reads the chain with the legal-entity scope `*` whatever scope the caller set (the owner is not a superuser, so forced row-level security binds it too), and gives the caller its scope back. Its `search_path` is pinned to `pg_catalog`, the audit schema and `pg_temp` last, and its body names the schema, so a caller's temp table or view named `audit_entry` or `audit_anchor` never reaches it (with `pg_temp` left out, as `0011`'s `FROM CURRENT` did, PostgreSQL searches it first, and a temp view could run code as the owner). Under the per-tenant append lock it reads the chain head (seq and hash) itself, refuses a seq that is not the head (40001, and the job walks again) and any date but today or yesterday (UTC). No caller can therefore anchor a head the chain does not hold. One residual: the verdict columns are the caller's report, and `depot_app` could claim today's anchor early with the then-current head; the newer head is then anchored the next day (runbook). `tools/rlscheck` fails any SECURITY DEFINER function whose `search_path` is unset or does not end with `pg_temp`. The job exits non-zero when any chain has a break: runbook `docs/ops/runbooks/audit-chain-verify-failure.md`. A chain that is rewritten after an anchor (every hash recomputed) or cut short fails `:verify` on that anchor. Export of the anchors to object-locked storage is not built (NOT-IMPLEMENTED).

**Adding an audited table (B-07 parts b and c, B-36)** is wiring only, listed in `internal/cdc/tables.go`: the owning service routes the transactions that change the table through `auditctx.WithAuditedTx`, calls `auditctx.ConfigureSigner` at start with its service signing key configured, and adds a migration (REPLICA IDENTITY FULL, `ALTER PUBLICATION depot_audit_<service> ADD TABLE`, a column-level SELECT without P3 columns for `debezium_cdc_<service>`; party `0021` is the model); `deploy/kafka/connect.yaml` lists the table (and its P3 columns) on the service's `audit-cdc-<service>` connector, or gets a new connector and KafkaTopic copied from `audit-cdc-party` plus a Read ACL in `deploy/kafka/audit-consumer.yaml`; the service's public key goes into the audit chart's `serviceIdentity.publicKeys`; the registry gets the entry. `deploy/scripts/test_argocd_apps.py` (`test_audit_cdc_connectors_match_their_tables_and_the_consumer`) fails when they disagree.

**Rollout, and no rollback past B-07a.** Migration `0009` adds the legal-entity policy. A B-06 image running against it reads the chain head under its caller's legal-entity scope; once the head row belongs to another legal entity, it links to an older row and forks the chain, for good (the table is append-only). So: roll this release out as B-06's, with `strategy.type=Recreate` for the release only, and **do not roll audit back past B-07a once any row with a legal entity exists** (a change from a token naming one legal entity, or any captured change). Roll forward instead. A `fork` (or a `link-mismatch`) found right after a rollout or rollback window is this, not tampering: the runbook says how to tell. The connector `audit-cdc-party` is created stopped (`state: stopped`); start it (`state: running`) together with the chart's `consumer.enabled` in the same environment, and the CronJob (`chainNightly.enabled`) with the tenant list. A running connector without its consumer lets captured changes age out of the topic (30 days) without reaching the chain. The connector sends a heartbeat every minute (a non-transactional logical message, no table needed) so its slot does not hold WAL back while the captured table is quiet.

Metrics (consumer admin port): the platform `event_consumer_*{consumer="audit-cdc"}` series, `audit_cdc_changes_recorded_total`, `audit_cdc_changes_unattributed_total`, `audit_cdc_changes_bad_signature_total`, `audit_cdc_contexts_recorded_total`, `audit_cdc_contexts_rejected_total`.


## PHI read-access log (#606, HIPAA overlay)

HIPAA audit controls ask who looked at protected health information, not only who changed it. A service that returns a record with `phi` fields (see `services/metadata`) records the read with `POST /v1/audit/reads`: `entity`, `recordId`, `fields[]`, `purpose` (required, a reason code or free text up to 500 characters), and optionally `traceId` (default: the request id) and `occurredAt` (default: now, at most five minutes ahead). The reader is the verified caller of the request (the `act` of a service token), never the body: a body that sets `userId` is refused with AUD-0002. `sourceService` is the verified service that recorded the read. `platform/go/phiaudit` is the client and the fake for tests.

`phi_read` (migration `0003_phi_read.sql`) is per-tenant, row-level secured and append-only: a trigger rejects update, delete and truncate, and `depot_app` holds only `SELECT` and `INSERT`. Each row carries `prev_hash` and `hash` (SHA-256 over a JSON array of the previous hash and the row, so no value can shift into its neighbour); appends are serialised per tenant with an advisory lock so the chain cannot fork. An edited, removed or reordered row breaks the chain at that position.

`GET /v1/audit/reads` lists rows in chain order, filtered by `entity`, `recordId`, `userId`, `from` (inclusive) and `to` (exclusive), `limit` (1 to 500, default 100) and `cursor` (the `nextCursor` of the previous page). `GET /v1/audit/reads:export?format=csv|ndjson` streams the tenant's rows (same filters) for an auditor. Before streaming it verifies the whole chain from the genesis hash and reports the verdict in the headers `X-Depot-Read-Chain-Verified`, `-Entries`, `-Head` and, when broken, `-Broken-At`; `GET /v1/audit/reads:verify` returns the same verdict as JSON. `-Entries` and `-Head` describe the whole chain that was verified, not the filtered rows. The body's completeness is in the trailers `X-Depot-Read-Export-Rows` and `X-Depot-Read-Export-Complete: true`, sent only after the last row; if the export fails once rows are streaming, the connection is aborted, so a body without the completion trailer is incomplete. An auditor keeps the head hash from each export: a later chain that does not contain it was cut short (a chain alone cannot show that rows were removed from its end). CSV prefixes a cell that starts with `=`, `+`, `-`, `@`, tab or carriage return with an apostrophe so a spreadsheet does not run it as a formula; NDJSON is lossless, so recompute hashes from it. Read-log rows are not published as events: they would copy PHI access metadata onto the bus.

**Break-glass review (HIPAA emergency access).** A read recorded with the reserved reason code `BREAK-GLASS` as its purpose (`BREAK-GLASS` alone, or followed by `:` or a space and the reason) is emergency access: in `hr`, a person without `hr.worker.inquire` reads another worker's benefits under `hr.benefits.break-glass`, a duty kept for emergencies. `GET /v1/audit/reads:break-glass` lists those reads oldest first (`status=pending`, the default, is the review queue; `reviewed`; `all`; `limit`, `cursor` as above), and `POST /v1/audit/reads/{id}:review` with `{"outcome": "APPROVED" | "FLAGGED", "note": "..."}` records a second person's review, once; FLAGGED needs a note. The reviewer is the verified caller and may not be the reader (AUD-0005, as for a read that is not break-glass or is already reviewed; two racing reviews meet at the primary key and the loser gets AUD-0005). The review is a row in `phi_read_review` (migration `0004_phi_read_review.sql`): row-level secured, append-only (trigger; `depot_app` holds `SELECT` and `INSERT`), keyed by the read, so the `phi_read` chain is untouched and still verifies.

Metrics: `audit_phi_reads_recorded_total`, `audit_phi_reads_failed_total`, `audit_phi_read_exports_total`, `audit_phi_break_glass_reviews_total`. To accept `hr` service tokens set `serviceIdentity.publicKeys` in the chart (`DEPOT_SERVICE_NAME=audit`, `DEPOT_SERVICE_PUBLIC_KEYS`).

## Error codes

| Code | Status | Meaning |
|---|---|---|
| COM-0001 | 400 | malformed body or missing change fields |
| AUTH-0001, AUTH-0003, COM-0500 | 401, 403, 500 | missing tenant, duty missing, internal error |
| AUD-0001 | 422 | domain rejection (invalid change, checkout rules) |
| AUD-0002 | 422 | a read-log or change request named the reader or actor (`userId`); it is always the verified caller |
| AUD-0003 | 400 | invalid read-log filter: time range, `limit`, `cursor` or export `format`, or break-glass `status` |
| AUD-0004 | 404 | a break-glass review named a read this tenant's log does not hold |
| AUD-0005 | 409 | a break-glass review that may not be made: the read is not break-glass, is already reviewed, or the reviewer is the reader |
| AUD-0006 | 422 | a change claimed an `onBehalfOf` or `actorKind` the verified caller cannot vouch for: `onBehalfOf` from a service acting on its own, or not the user the service token carries; an `actorKind` other than the caller's |
| AUD-0007 | 403 | a change was sent without a verified service token; identity headers are not accepted on `POST /v1/audit/changes` |
| AUD-0008 | 400 | `GET /v1/audit/records:verify` with a `fromSeq` or `toSeq` that is not a positive integer, or `toSeq` before `fromSeq` |
| AUD-0009 | 403 | `GET /v1/audit/records:verify` from a caller without tenant-wide authority: the verdict describes every legal entity of the tenant |
| COM-0001 | 400 | read-log entry failed validation (missing or over-long `purpose`, `fields`, `entity`, `recordId`; `occurredAt` in the future) |

Metrics: `audit_changes_applied_total`, `audit_changes_failed_total`.
