# Not implemented after Wave 14 slice B

Slice B of #436 ships period maintain/reopen, the checklist HTTP API, allocation run/post/reverse, accrual apply with automatic reversals, and regrouping. Remaining items are follow-ups, not a second close slice.

| Deliverable or AC | Status | Reason |
|---|---|---|
| AC1 / Deliverable 1: period control | built | `GET /v1/close/periods`, `PATCH .../modules/{module}`, dual-approval reopen (`:request-reopen` / `:approve` / `:reject`) and an in-process sweeper (`ExpireReopened` via `close_reopen_due_tenants()`) consume `CLOSE_REOPEN_*` and `CLOSE_LOCK_WAIT_MS`. Closed periods reopen only through that workflow. `dev.depot.close.period.statuschanged.v1` is written to the outbox with the transition. Temporal is not a close-module dependency; expiry is the sweeper. Every transition and the opening reopen approval set the ledger's period lock before they commit and answer only after the ledger confirmed it (FR-14.1, B-08c; 503 `CLOSE-0012` and no change when the ledger does not), so no posting commits into a period after close reported it closed. The harness that drives a ledger post into a just-closed period (#441) is `services/ledger/internal/closeperiods/harness_test.go`; it runs the ledger's real API and store against a fake close service, not the two deployed services. Not built: registering a period does not set a lock (until its first transition the ledger checks the period with close alone), and allowed-group forwarding for `on_hold` (the ledger refuses on hold unless `ledger.period.postclosed`). |
| AC2 / Deliverable 3: allocation run/post | built | Rules persist; `POST /v1/close/allocation-runs` proposes from the ledger trial balance and posts through `ledgerclient` with `PostClosed` false. `:post` and `:reverse` use the same path. Closed periods are refused in close (`LEDGER-0013`) before the ledger is called. |
| AC3 / Deliverable 5: year-end close | built (slice A) | Unchanged. Duties `close.yearend.run` / `close.yearend.read` stay unattached. |
| AC4 / Deliverable 2: close checklist | built | Templates, runs, the task board and start/complete/skip/reassign persist on the 0002 tables. The web status board is still a navigation stub. |
| Deliverable 4: accruals | built | Schemes persist; the amount lives on the scheme (`close.accrual.write`), `:apply` spreads it (equal / by_days / custom, month-end stepping, ledger currency only) and posts the occurrences and reversals that are due through `ledgerclient` without `PostClosed`, persisting each entry id as it posts. The in-process sweeper posts the rest as they fall due, with backoff, and parks a run on a permanent ledger refusal. Recurring journals already live in the ledger service and are not duplicated here. |
| Deliverable 6: regrouping | built | Remaining-term, debit/credit balance and account-balance-sign rules persist and post through `ledgerclient` without `PostClosed`. Each rule posts once per ledger and key date (`CLOSE-0010`), claimed before the ledger is called. Item-based rules (remaining-term, debit/credit balance) return 503 until an open-item source is wired; an empty proposal is never posted. A source with a credit balance books the reclassification with the sides flipped. Remaining-term items with no due date fall into the shortest bucket (BR-14.13). Ledger open items do not expose a due date on the current client; remaining-term in production needs that field from ledger (a ledger-side change, now that #441's harness is built). |
