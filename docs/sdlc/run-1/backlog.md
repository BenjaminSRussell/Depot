## E1. Identity, access and data isolation

### B-01 — Close the forged-identity path: default-deny NetworkPolicies and signed service calls between peers

**Labels:** `sdlc-run-1`, `P0`, `area:deploy`, `area:platform`, `security`, `architecture`  
**Size:** L (split: a. NetworkPolicies + CI check; b. signed peer calls)  
**Why P0:** Forged identity in audit rows (A4): security and audit integrity.

**Problem.** Services believe whatever `X-Depot-User`, `X-Depot-Tenant` and `X-Depot-Duties` headers they receive, because the gateway is supposed to be the only way in. In Kubernetes that is not true: only 13 of 69 charts have a NetworkPolicy, no namespace denies traffic by default, and 67 charts share the `hello-ledger` namespace. Any pod there can call a service as any user, and the audit rows will name that user as if they acted. Four services (receiving, payables, party, product) also forward user headers to peers instead of using signed service tokens, which keeps the door open. Receiving also asserts duties it invents when it calls peers (`receiving/internal/periods/periods.go:111`, `receiving/internal/tax/tax.go:223`).

**Scope — in:**
- A default-deny ingress NetworkPolicy in every namespace that runs a Depot service, plus gateway-only and generated peer allow rules in every service chart (`services/*/charts/*/templates/networkpolicy.yaml`)
- Generate the peer allow-list from the ADR-0010 grant table
- CI check that fails on a chart without the policy
- Move receiving, payables, party and product peer calls that forward user headers to Ed25519 service tokens; remove party's header-forwarding fallback to numbering
- Record per environment whether `DEPOT_GATEWAY_SECRET` is also required in Kubernetes, and wire it if yes

**Scope — out:**
- Temporal frontend mTLS (B-12)
- Gateway enforcement model (B-04)

**Acceptance criteria:**
- [ ] (D1 exit) Every namespace that runs a Depot service has default-deny ingress and gateway-plus-generated-peer allow rules
- [ ] (D1 exit) A CI check (`deploy/ci` or `tools/`) fails on a chart without them; fixture test with one chart missing the policy
- [ ] (D1 exit) An integration test sends a forged-header call from a non-peer pod and it is refused
- [ ] No service sends an `X-Depot-*` identity header (user, tenant, duties, legal entity) to a peer outside the gateways; a grep test in CI enforces it, covering receiving's synthesized `X-Depot-Duties` (`periods.go`, `tax.go`); peer calls carry `X-Depot-Service-Token`
- [ ] Party's call to numbering always uses a service token (unit test with the token verifier)

**Traces:**

- Architecture gaps: D1
- ADR backlog bullets: ADR-0006 #1, ADR-0006 #2, ADR-0006 #3, ADR-0010 #2, ADR-0010 #4, ADR-0015 #4
- UX: A4

**Dependencies:** None  
**Blocked-external:** The forged-header refusal on a live cluster is #213; the integration test runs on k3d in CI.

### B-03 — Enforce legal-entity scope end to end and let multi-company users switch company safely

**Labels:** `sdlc-run-1`, `P0`, `area:platform`, `area:identity`, `security`, `architecture`, `defect`  
**Size:** L (split: a. kernel no-claim guard, ships first; b. OPA legal-entity rule, scoped assignments, RLS gaps; c. list model after owner confirmation)  
**Why P0:** Data isolation between companies; kernel guard is a live defect (RR-01).

**Problem.** Company data must stay inside the companies a person is entitled to. Today three things are wrong. (1) When a token has no `le` claim, the kernel accepts the shell's `X-Depot-LegalEntity` header as the scope (`platform/go/tenant/tenant.go`, `requestLegalEntity`), so only the gateways stop a caller from choosing any company. (2) The OPA policy has no legal-entity rule and scoped role assignments are left out of the bundle, so a per-company role grants nothing in OPA. (3) Several services (shopfloor pay data, scheduling, audit, mobile, fx, integration-hub-ts, agents-ts) have no legal-entity column or policy. Separately, a user entitled to several companies cannot switch company at all and needs one account per company.

**Scope — in:**
- Part a (first, or in the same release, before Envoy forwards the selection header): the kernel refuses a legal-entity selection when the token has no `le` claim (`platform/go/tenant/tenant.go:241-243`), keeping tenant administrators working
- Part b: legal-entity rule in `policies/authz/authz.rego`, scoped assignments in the compiled bundle, `pv` claim decision; legal-entity policy or `rlsexempt` reason for every table listed in D17 (the audit tables are done inside B-07, which owns `services/audit/migrations` in the same wave); `tools/rlscheck` green; FORCE ROW LEVEL SECURITY on the standing exceptions (`service_token_replay` and the rest) or a recorded `rlsexempt` reason (FR-2.4)
- Part c (after owners confirm ADR-0006 rule 4): `le` becomes the list of entitled legal entities (realm mapper), membership check in the kernel, devgateway and `depot-server`, Envoy forwards the selection, shell company switcher

**Scope — out:**
- Dimension-level security inside one company (B-19)
- Changing the enforcement model of the gateways (B-04)

- [ ] OPA: `authz_test.rego` cases show a role scoped to company A grants nothing in company B and grants in A
- [ ] (D33 exit) Owners confirm the model; then an end-to-end test signs in a user entitled to two legal entities, switches company in the shell and reads and writes in each through Envoy, devgateway and `depot-server`; a selection outside the entitled list is refused with 403 on all three paths; a request with no `le` claim and a selection is refused

### B-04 — One authorization enforcement model across the three gateways, with a logged allow/deny record per decision

**Labels:** `sdlc-run-1`, `P0`, `area:platform`, `area:gateway`, `security`, `audit`, `architecture`  
**Size:** M  
**Why P0:** Audit integrity: authorization decisions are not reconstructable (A1).

**Problem.** An auditor cannot answer "who was refused or allowed what, and when". OPA decision logs are off, Kubernetes makes no OPA decision at all, `authz.RequireDuty` writes a 403 but no record, and Envoy logs no subject. The three gateways (Envoy, devgateway, `depot-server`) also check different things, so a route that is refused on Windows may be allowed in Kubernetes.

**Scope — in:**
- Choose one model (all OPA, or all duty headers) and implement it in Envoy, devgateway and `depot-server`
- A shared route-table test that all three gateways pass
- Structured allow/deny record from `authz.Require` and the three gateways: pseudonymized subject, tenant, duty, route, outcome, request id; shipped and retained by class
- `depot_authz_denied_total` metric and alert

**Scope — out:**
- Legal-entity rule content (B-03)
- Audit trail of data changes (B-07)

**Acceptance criteria:**
- [ ] (D23 exit) One enforcement model; the three gateways pass the same route-table test
- [ ] (D36 exit) `authz.Require` and the three gateways emit one structured allow/deny record per decision (pseudonymized subject, tenant, duty, route, outcome, request id), shipped to the log store and retained by class, plus `depot_authz_denied_total`; a test asserts a denied call produces the record
- [ ] The record uses `platform/go/logpseudo` for the subject; a unit test shows no raw user id in the record

**Traces:**
- Closes: FR-2.7 (Must, Partial) — one decision model: duties from headers vs OPA decided and uniform
- Related (not counted): FR-2.6
- Architecture gaps: D23, D36
